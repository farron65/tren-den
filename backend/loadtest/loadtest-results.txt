TREN DEN LOAD TEST: before vs after the async migration
=======================================================
sync  = main at b90421c (before PR #2): async def endpoints calling the
        blocking session.exec(), psycopg2, sync def dependencies
async = main at eb12a14 (after PR #2): AsyncSession + asyncpg

Sync vs async sections: earlier runs, raw data not kept.
Bcrypt fix section: results/results_before_mine.json and results_mine.json.

SETUP
- Same machine (Windows), Postgres 18 in Docker, 1 uvicorn worker each,
  access logs off. Default SQLAlchemy pool (5 + 10 overflow = 15 connections).
- Each version gets its own fresh DB seeded with the same data:
  20 users x 30 workouts (4 exercises x 3 sets).
- Closed loop: N virtual users each send a request, wait for the answer,
  send the next. 3s warmup, then 20s measured. Client timeout 60s.
- Sync login and writes were rerun on a fresh server, because after its
  first deadlock the sync server never recovered.
- The load generator ran on the same machine, so absolute numbers are
  lower than a real server would give. Compare the two versions with each
  other, not with production.

SUMMARY
1. Sync DEADLOCKS under load; async doesn't.
   Sync froze completely (0 requests completed) at 100 users on reads,
   50 users on login, and 100 users on writes, and stayed frozen afterwards.
   Async kept serving at every level tested.
   Why: sync's dependencies (get_session, get_current_user) run on FastAPI's
   40-thread pool. Once more requests are in flight than there are DB
   connections (15), the extra threads block waiting for a connection. A
   connection is only released when get_session's cleanup runs, and that
   cleanup needs a thread from the same, now-full, pool. Nothing can finish
   until SQLAlchemy's 30s pool timeout fails the waiting requests.

2. Async is ~1.5x faster on reads and ~1.6-1.8x faster on writes before
   sync breaks (10-50 users), with lower median latency throughout.

3. Async's TAIL latency is worse on reads at 50 users (p95 1.2s vs 0.7s).
   Async lets every request run at once, so they all compete for the same
   15 DB connections; most are fast (p50 ~100ms) but the unlucky ones queue.
   Sync was "protected" by being stuck doing one thing at a time.
   Next lever: pool size, and what each request holds a connection for.

4. LOGIN DID NOT IMPROVE: ~4 logins/sec on both versions.
   bcrypt.checkpw (~250ms) runs directly in the async endpoint and blocks
   the event loop, so every other request waits while one password is
   checked. At 100 users a login takes up to 34s, and it slows down every
   other endpoint while it runs. The async migration can't fix this. Next
   step: run the hash check off the event loop (asyncio.to_thread /
   run_in_threadpool) and re-measure.
   -> DONE: see BCRYPT FIX at the bottom (~5/s -> ~54/s).

BCRYPT FIX: login before vs after running bcrypt in a thread
============================================================
before = main at a10a950: bcrypt.checkpw called directly in async code
after  = asyncio.to_thread(verify_password, ...) / to_thread(hash_password, ...)
Same setup as above; fresh DB and fresh server for each. Machine has
20 logical cores; asyncio.to_thread's default pool has 24 threads.
Raw data: results/results_before_mine.json, results/results_mine.json

WHAT CHANGED
- Login throughput went from ~4-6/s to ~38/s at 10 users and ~54/s at
  50-100 users (about 7-15x). Before, the event loop checked one
  password at a time; now several bcrypt checks run in parallel threads
  (bcrypt releases the GIL while hashing), and the event loop stays free
  to serve other requests in the meantime.
- At 100 users, median login latency fell from 14.4s to 1.7s and p95
  from 23.7s to 4.2s.
- A single login is NOT faster: each check is still ~250ms of CPU work
  (one-at-a-time manual tests show ~200ms both before and after). The
  fix only helps when many requests arrive at once.
- It levels off around 54/s instead of scaling to 20 cores: bcrypt is
  CPU-bound, and the load generator was competing for the same CPU.
  On Render (fewer cores) the ceiling will be lower, but the event loop
  no longer freezes while passwords are checked.
